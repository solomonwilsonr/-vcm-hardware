Every hardware change has a blast radius.

VCM is version control for datacenter hardware. Commit a node's configuration the way you commit code, and it tells you what the change breaks, which physical units are affected, and how much to trust every single thing it says.

What it does

Three questions, answered from your files

A node is described by a manifest you commit. Accelerators, CPUs, memory, NICs and power supplies are components; the things they share are power domains, PCIe roots and fabrics.

01

What exactly changed?

A semantic diff of the inventory — models, part numbers, slots, form factors and the connections between them. Not changed bytes in a JSON file.

02

What else does it touch?

A dependency graph plus rules for power budget under a redundancy policy, chassis cooling, PCIe generation and lanes, driver minimums and connector changes.

03

Which units are affected?

Releases pin every file by hash. Units are registered against releases, so a recall is a query rather than an archaeology project.

Built on Appwrite

A fleet is not a folder on your laptop

The design history belongs in your checkout. The fleet does not. "Which of our units carry this part?" is a question about every machine, so the unit and rack registry lives in Appwrite TablesDB and the local JSON is demoted to a cache.

  • Writes fail closed. A unit the fleet never accepted must not exist locally either.
  • Reads degrade open, and say fleet: LOCAL CACHE, possibly stale when they do.
  • Duplicate serials are refused across machines, not just within one checkout.
  • A unit built from a revision this clone never fetched reports UNRESOLVED rather than quietly answering for a partial fleet.
two checkouts, one fleet
$ alice/  vcm device register NODE-0001
$ bob/    vcm device register NODE-0002

$ bob/    vcm device list --local
NODE-0002   ← bob's cache holds only his own

$ bob/    vcm device affected --component GPU0
NODE-0001   ← alice's
NODE-0002
2 unit(s)  ← bob answers for the whole fleet

With a per-clone registry, this is exactly where
a recall quietly under-reports.
Confidence

Every finding says how much to believe it

This is the core claim. A tool that tells you what might break is only useful if you can tell how much to trust each thing it says, so the class is never implied — it is labelled, shaped and cited.

VERIFIED RULE-BASED SPECULATIVE

verified

Derived from parsed configuration data, declared project links or stored evidence. A fact about your files.

rule_based

A heuristic from engineering rules and the component catalog. Cites the catalog entry and whether anyone has checked it against a datasheet.

speculative

A prediction, not established by data. An optional LLM provider can only ever add these — never the other two.

Silence is never safety

If a changed component is not in the catalog, VCM says so outright instead of returning a clean-looking report. It names which checks were skipped and which still ran on declared values, because a reader must never confuse the rules passed with no rules ran.

Honest scope

What it is not, yet

Everything the README marks Implemented runs and is covered by tests. Everything else it marks Planned. The same applies here.

The catalog is small and unreviewed

90 parts, and none has been checked against a datasheet by a human. Every entry carries reviewed: false and a named source. Thermal figures are package-typical estimates; TDP is a board rating, not measured draw.

Rules are heuristics

They can be wrong or incomplete. VCM discloses what it does not know; it cannot disclose what it has wrong.

Semantic search is unverified live

Part search on VectorsDB is implemented but has not been exercised against the real service, because the API key used in development lacked the embedding scopes.
