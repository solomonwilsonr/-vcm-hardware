How it works

Three commands from change to consequence

1

Commit the configuration

Snapshot a node manifest the way you snapshot code. Every file is pinned by hash.

vcm commit -m "v1.1" --tag v1.1
2

See what the change breaks

Compare two revisions. Each finding says whether it is verified, rule-based or a guess.

vcm impact v1.0 v1.1
3

Trace the physical units

Ask which registered machines carry an affected part, across the whole fleet.

vcm device affected --component GPU0
01 — What changed

A diff that knows what a node is

Accelerators, CPUs, memory, NICs and power supplies are components. The things they share are power domains, PCIe roots and fabrics. Change one and VCM compares the engineering meaning, not the bytes.

Inventory

Models and part numbers

Replacements, additions, removals and quantity shifts, grouped so eight identical GPUs report once rather than eight times.

Fit

Slots and form factors

A changed slot or form factor means physical rework, and the rollback planner says so in the right words for the domain.

Topology

Connections

Which power domain, which PCIe root, which fabric — and what moved between them.

02 — Blast radius

Follow the change outward

A dependency graph links every component to the domains it sits on, the firmware pinned to it and the tests that validate it. Changing one part walks outward from there.

  • Hops are counted, so a direct neighbour is never confused with a distant one.
  • Globally shared domains are not followed. Every component sits on the PSU bank, exactly as every part sits on ground — following it would report the whole node.
  • Firmware and tests come along. If a change reaches a component your firmware is pinned to, that is a finding with the file and hash attached.
change to GPU0 → 10 components across 2 hops
03 — The rules

Arithmetic nobody wrote down

PSU_BANK declared draw 4190 W budget 4000 W
8000 W installed · 4000 W usable under 2+2 redundancy

Rules read the manifest first and the catalog second, so a site that has measured its own numbers wins over a general part spec.

  • Power budget under the declared redundancy policy — 2+2 means two supplies carry the load, not four.
  • Chassis cooling against declared draw.
  • PCIe generation and lane budget against the host root.
  • Driver and CUDA minimums for every accelerator installed.
  • Power connector changes, because a harness that does not fit is not a drop-in.
04 — Confidence

Every finding says how much to believe it

This is the core claim. A tool that tells you what might break is only useful if you can tell how much to trust each thing it says, so the class is never implied — it is labelled, shaped and cited.

VERIFIED RULE-BASED SPECULATIVE

verified

Derived from parsed configuration data, declared links or stored evidence. A fact about your files, with the hash to prove it.

rule_based

A heuristic from engineering rules and the catalog. Cites the entry it leaned on and whether a human ever checked it.

speculative

A prediction, not established by data. An optional LLM provider can only ever add these — never the other two.

Silence is never safety

If a changed component is not in the catalog, VCM says so outright instead of returning a clean-looking report. It names which checks were skipped and which still ran on declared values, because a reader must never confuse the rules passed with no rules ran.

05 — Built on Appwrite

A fleet is not a folder on your laptop

The design history belongs in your checkout. The fleet does not. "Which of our units carry this part?" is a question about every machine, so the unit and rack registry lives in Appwrite TablesDB and the local JSON is demoted to a cache.

  • Writes fail closed. A unit the fleet never accepted must not exist locally either.
  • Reads degrade open, and say fleet: LOCAL CACHE, possibly stale when they do.
  • Duplicate serials are refused across machines, not just within one checkout.
  • A unit built from a revision this clone never fetched reports UNRESOLVED rather than quietly answering for a partial fleet.
both register · both can answer for the whole fleet

Agents

Agents propose. People decide.

Connect an AI agent over MCP and it can read everything VCM knows: diffs, impact reports, drift, the fleet. What it can write is a proposal, and nothing more. A named person decides, and the audit log records who.

Read-only by construction

Every tool but one cannot change anything. A test fails if a tool name contains approve, sign, commit, push or lock.

Checked before it is believed

A claim checker recomputes the report from the repository, so an agent cannot quote a finding that does not exist or upgrade a guess to a fact.

Not yet driven by a live agent

It has been tested over the protocol and a scripted client. The evals have only met reference answerers. The dashboard's Agents page is where a person decides.

06 — The rest of it

Everything around the change

Releases

Pinned and signed

Manifests pin every file by hash. Ed25519 signatures and a hash-chained audit log make a release something you can prove, not just re-hash.

Lineage

Units and recalls

Every unit is registered against a release, with a passport and QR. Ask which units carry a part and get an answer grouped by the variant actually fitted.

Rollback

What is reversible

Splits a change into software-reversible, physical rework and platform change — and lists the units not yet at the target revision.

Reality

Redfish and nvidia-smi

Import what the machine actually reports and compare it to the manifest. Drift is a finding, so a report never reasons about a node that does not exist.

Fleet

Racks and rollout

Rack power budgets before and after a change, rollout waves, and queries across every registered unit.

Interfaces

CLI, API, dashboard, MCP

A vcm command, an authenticated REST API with roles, an offline dashboard, and an MCP server so an agent can read freely and propose — a person decides.

07 — Honest scope

What it is not, yet

Everything the README marks Implemented runs and is covered by tests. Everything else it marks Planned. The same applies here.

The catalog is small and unreviewed

90 parts, and none has been checked against a datasheet by a human. Every entry carries reviewed: false and a named source. Thermal figures are package-typical estimates; TDP is a board rating, not measured draw.

Rules are heuristics

They can be wrong or incomplete. VCM discloses what it does not know; it cannot disclose what it has wrong.

Semantic search is unverified live

Part search on VectorsDB is implemented but has not been exercised against the real service, because the key used in development lacked the embedding scopes.
